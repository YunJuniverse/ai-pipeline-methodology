# 23. 검증 규범

> "검증했다"가 실제로 무엇을 보증해야 하는가의 규칙. 2026-07 전 레포 월간 전수조사(11개 repo·마찰 302건)에서
> **무음 실패(P4, 6개 repo)·빈 상태 검증(P9, 5개 repo)·검증불가 방치(P12, 4개 repo)**가 반복 손실원으로 실증되어 신설(METH-123).
> 핵심 가치: **성공처럼 보이는 실패를 성공으로 세지 않는다. 검증 못 한 것을 됐다고 말하지 않는다.**

---

## 1. 무음 실패 프로토콜 — "성공처럼 보이는 실패"를 잡는 5규칙

실사고 계보: `.catch(()=>[])`가 수익 표면 소등 은폐(gamblescan)·Vercel 한도 무음 스킵·zsh 루프 오작동·빈 스크린샷(talmo)·키 오매칭 무에러 null(ai-icons 40분)·빌드 실패해도 구버전으로 조용히 성공(icons-invest).

1. **0건 처리 = 실패.** 일괄 처리·수집·변환 스크립트는 "N건 처리"의 N이 0이거나 기대 하한 미달이면 실패로 종료한다(sanity assert). "에러 없음"은 "작동함"이 아니다.
2. **검사 못 함 ≠ 깨끗함.** 검사기가 대상 파일을 0개 찾으면 통과가 아니라 exit 1이다 — 가드가 헛도는 상태와 실제로 깨끗한 상태를 구분한다.
3. **금지형 가드는 negative case로 실효를 증명한다.** 가드 신설 시 위반을 일부러 주입 → 정확히 그 지점을 지목하며 실패하는지 확인 → git diff로 원복 검증. 통과만 하는 가드는 아무것도 보증하지 않는다.
4. **대리 신호를 사실로 쓰지 않는다.** 확인 행위가 *실제 값을 지나가야* 한다 — 요약 도구의 출력·컬럼 이름·존재 카운트는 원본이 아니라 원본의 그림자다. 사실로 기록·배포하기 전에 원문·실값·렌더를 직접 지난다. **틀린 기록은 후속 계획으로 전파된다.** 실사고 계보(gamblescan 누적 5건): WebFetch 요약이 "이름만"이라 했으나 원문 HTML엔 도메인 15개 · 컬럼명 `published_withdrawal_min`을 '최소출금액'으로 단정했으나 실값은 처리시간(분)이라 3개 문서·후속 계획에 오정보 전파 · `head:true` 카운트 쿼리는 **없는 테이블에도 오류를 내지 않아** 존재하지 않는 테이블을 "있다"로 통과시킴 · 검증 출력이 slug만 찍어 정작 깨진 필드(2,384건 전량 필터)를 지나치지 않음. **도구가 다르면 사본도 다르다** — 같은 URL 이라도 `curl` 무쿠키 요청과 브라우저 요청은 엣지에서 다른 변형 사본을 받는다. curl 6/6 이 "없음"이라 해서 '원복 실패'로 2회 오판했고, 브라우저 2/2 는 신선한 사본을 보고 있었다(cafe24-renewal). **판정은 사용자가 실제로 지나는 경로로 한다.** 같은 이유로 **테스트 결과는 출력 문자열이 아니라 exit code 로 판정**한다 — `| grep 통과` 는 실패 문자열도 매치해 빨간 테스트를 통과로 넘긴다(icons: 버튼 등록부 미분류 상태로 머지 → 복구 PR). 성공 토큰을 굳이 본다면 앵커(`^통과`)로만.
5. **빌드 통과 ≠ 산출물 정상.** 패치 후에는 산출물을 리드백한다 — 프로덕션 빌드 CSS grep(Lightning CSS가 미참조 변수를 제거), pdftotext/셰이프 스캔(pptx 재배열 실패가 구버전으로 조용히 성공), 배포 후 실서빙 확인(배포 한도 무음 스킵). **외부 쓰기 도구는 쓰기 후 read-back 으로 대조한다** — 노션 미러류가 전송 중 비ASCII(한글) 음절을 변형한 사례가 3회(cafe24-renewal, ~115분). 변형된 음절을 매칭 문자열로 재전송하면 또 변형된다 — read-back 없이는 오염 사실조차 모른다. **리드백은 배포가 도달한 뒤에 한다** — 업로드 직후 측정은 옛 사본을 재확인할 뿐이다. 버전 토큰을 심어 그 값이 관측될 때까지 폴링한 **뒤에** 측정한다(cafe24-renewal: SFTP 성공에서 웹 반영까지 ~50초). 에러 삼킴(`.catch`·`|| true`·`2>/dev/null`)은 실패를 침묵시키는 결합이다 — 삼킬 때는 반드시 대체 신호(로그·카운트)를 남긴다.

6. **재발했거나 대외에 노출된 사고의 규칙은 문장이 아니라 차단 도구로 올린다** (METH-148). 기준: **같은 원인 재발 2회** 또는 **운영 화면·대외 노출 1회**. 그때부터 지침 조항은 «쓰여 있는 규칙»이 아니라 «실행 시 막는 도구»여야 한다 — 업로드 전 린트 차단 · 뷰포트 누출 감사 · 배포 가드 · 치환 건수 assert. 조항에는 **대응 도구 경로를 함께 적는다**(조항만 있고 도구가 없으면 그 조항은 아직 승급 전이다). 근거: cafe24-renewal 재발 표시 마찰 42건 1,005분(21%)이 «문장 규칙만 있던 구간»이었다(결제 페이지 주석 노출·헤더 누출은 차단 린터·감사 스크립트로 전환 후 멈췄다). 상류 자신도 같은 경로를 걸었다 — build-guard(METH-122, «SOP 문서만으로는 못 막았다») · wrap 구조 검증(METH-143) · 훅 읽기 전용(METH-146) · ship 공유 체크아웃 가드(METH-147). §1-3(가드는 negative case 로 실효 증명)과 한 쌍이다.

7. **대역 통과 ≠ 실제 통과** (METH-149). 모의 서버·가짜 엔진·대역 DB 위의 통과는 «대역과 코드가 맞는다»만 보증한다. 보고할 때 **«대역 기준»을 명시**하고, Done 조건에는 **실제 경로 1회**(실 엔진·실 API·실 러너)를 넣는다. 실사고 계보: 가짜 엔진 E2E 통과가 같은 원인으로 재발(ai-icons 70분) · 엔진이 Git 밖이라 CI 러너에서만 빌드 실패(ai-icons) · 모의 서버가 받아 준 인증 머리말을 실 API 가 거부해 SSO 401(icons-ax, 같은 원인 3회). **통합 코드를 고칠 때는 실패 원인 로그를 같이 심는다** — 다음 결함을 바로 진단한다(icons-ax #95 가 심은 기록으로 #123 즉시 진단).
8. **«건너뜀»·«성공» 표지는 실행의 증거가 아니다** (METH-149). 무인 작업은 **결과물의 신선도**(마지막 적재 일자·행 수·산출 시각)로 판정한다. 실사고: 주간 예약 작업이 3주 연속 첫 명령의 권한 승인 대기에서 끊겼는데 «성공»으로 기록 — 등록부 3주 미갱신·재채점 12일 정지, 운영 5xx 로 발견(gamblescan 155분) · 검증 재사용이 적중하면 배포 잡 전체가 skipped 인데 run 은 success(비적용 팀 repo). CI·배포 파이프라인은 **«필요한 잡이 실제로 돌았는가»**를 따로 단언하고, 모든 잡에 timeout 상한을 둔다(멈춘 설치 하나가 main 배포를 수 시간 막은 사례 — 상한은 실측 최대의 2배·5분 미만 금지). 무인 작업 계약은 지침 29 §9.
9. **프로브 도구 자체를 먼저 검증한다** (METH-149). 측정 도구가 거짓을 내면 판정 전체가 틀린다 — 구형 curl 의 TLS 미지원이 «000» 757건 오탐 · `sed` 로 뽑은 비밀번호가 «Access denied» 오탐 · 200 응답만 보고 정상 판정했으나 본문 131B(cafe24-renewal) · 국내 IP 로 수집해 차단 화면이 데이터에 섞임(gamblescan). 절차: ① 알려진 정상 대상 1건으로 프로브가 «정상»을 내는지 대조 ② 상태 코드가 아니라 **본문 바이트·기대 문자열 기준선**으로 판정 ③ 장애 판정 전 **자기 출구 IP·지역**부터 확인(VPN·해외 러너가 지역 방화벽에 막힌 사례 3건).
10. **전량 교체 적재는 축소를 거부한다** (METH-149). «0건 쓰기 = 전량 삭제»다. 교체형 적재는 0건 · 기존 대비 10% 초과 감소 · 미파싱 5% 초과면 exit 1 로 끝내고, 넘기려면 사람이 행을 대조한 뒤 명시 플래그(`--allow-shrink`)를 준다. 원형: gamblescan `scripts/sync-html-license-registries.ts`·`registry-replacement-guard`. §1-1(0건=실패)의 쓰기 측 대응물이다.

## 2. 상태 아닌 내용으로 검증한다 — UI·산출물 검증 5기준

실사고 계보: 데이터 0건이라 차트 파손 은폐(icons-marketing)·DOM 존재만 확인해 클리핑 버그 배포·URL만 믿어 404 스크린샷 채택(icons)·카드 크기 검수로 브랜드 라벨 놓침 75분(talmo)·RSC 스트리밍이라 HTML grep 거짓 음성(gamblescan)·가로 스크롤은 scrollWidth 실측으로만 검출(lifeManager).

1. **비어있지 않은 데이터로.** 빈 상태로만 검증한 화면·차트·목록은 검증되지 않은 것이다. 실물 규모에 가까운 데이터를 넣고 본다(스케일 의존 상수 — limit·임계값·풀 크기 — 는 데이터 N배 확장 시 전수 재검토).
2. **최대 표시 크기로.** 이미지·시각 자산 검수는 실제 최대 표시 크기 기준(썸네일 검수로는 히어로 결함을 못 본다). 반응형은 넘침 + 줄나눔 품질 + `scrollWidth` 실측까지.
3. **존재가 아니라 내용·가시성으로.** "200이 뜬다·DOM에 있다·URL이 맞다"가 아니라 **기대한 내용이 실제로 보이는가** — `textContent` 는 `display:none` 자식까지 포함하므로 그것만으로는 노출 판정이 안 된다. 요소별로 `display`·`offsetHeight` 를 함께 덤프해 판정한다(cafe24-renewal) — 제목 텍스트 어서션, `elementFromPoint`/스크린샷 가시성, 스트리밍 SSR은 HTML grep 대신 페이로드 구조 또는 브라우저. 성능 검증은 "좋아졌다"가 아니라 **"예측한 곳에서 예측한 만큼"**(가설-일치 확인).
4. **성능은 워밍 후 다회 표본의 중앙값으로.** 단회 측정은 개선을 역전시켜 보고한다 — 미들웨어 최적화에서 첫 측정이 개선안을 더 느리다고(111ms vs 88ms) 보고했으나 dev 컴파일 노이즈였고, 워밍 8회 + 표본 20회로 재니 53ms vs 82ms 로 뒤집혔다(lifeManager). **단회였다면 옳은 변경을 기각했을 것이다.** 분산(p25~p75)도 함께 보고해야 노이즈와 실제 개선을 구분할 수 있다.
5. **픽스처는 스키마가 실제로 만들어내는 특이값을 포함한다.** 값 매핑(null→기본값)이 있는 필드는 **그 기본값을 픽스처에 반드시 넣는다**. DB 뷰가 null 을 '기타'로 매핑하는 걸 알면서도 픽스처에 '기타'를 안 넣어, 집계 함수의 접기 바구니 이름이 실제 분류와 충돌하는 버그를 놓쳤다 — **테스트 20건이 전부 통과한 채 머지**되고 실화면에서야 범례·key 중복으로 드러났다(lifeManager). §2-1(실물 규모)이 *양*이라면 이것은 *모양*이다.

6. **부재 판정은 관측 조건을 먼저 검증한다** (METH-147). «없다·비었다·1개뿐» 판정은 그 관측이 성립하는 조건 아래서만 유효하다 — 지연로딩은 **실제 스크롤 입력 후** 측정(`scrollIntoView` 만으로는 1px 자리표시를 «빈 위젯»으로 오판) · 백그라운드 탭·UA·세션·표본 범위를 **판정문에 명시** · 부재 판정 전 스크린샷 육안 대조. 수치 0·1px 만으로 부재를 단정하지 않는다. 지침 24 §2 「부재와 미포착은 다르다」의 UI 절차다. 실사고 계보(cafe24-renewal, 월 9건 ~320분): lazy 이미지 높이 0 · 백그라운드 탭 rAF 정지 · 데스크톱 UA 에서 앱 미주입 · 내 세션 1페이지 vs 발주처 3페이지 · 표본 6파일로 «1개뿐» — 하나는 발주처 회신문안·최종 미팅 안건까지 오염(4일 방치).
7. **애니메이션·연출 실측은 보이는 컨텍스트에서만** (METH-147, catalog C-002). 숨은 브라우저 패널·백그라운드 탭은 rAF·CSS 애니메이션·스크롤 구동 타임라인이 얼어 **거짓값**을 낸다 — 정지점 6개의 `getAnimations()` progress 가 전부 1 로 읽혔으나 Playwright(visible) 에서는 0.95·0.01·복귀(icons). 연출·정지 위치 검증은 보이는 헤드리스 브라우저에서 rAF 대기 후 computed timing progress 로 잰다. **스크롤 구동 연출은 N px 단위 스크롤 스캔**(예: 5px)과 **겹침 프레임 스캔**(예: 40ms)으로 튐·잔상·겹침을 기계로 잡는다(cafe24-renewal: 도입 후 수렴). 값 조정으로 없앨 수 없는 **구조적 부작용**은 더 만지지 말고 되돌린 뒤 선택지를 수치와 함께 제시한다 — 수치 스펙은 지침 21 §2 wireframe-spec.

8. **외부 정본 편집은 내려받아 diff 로 대조한다** (METH-149). 스프레드시트·폼·게시 덱처럼 repo 밖 정본을 브라우저로 고친 뒤에는 **xlsx·사본을 내려받아 «바뀐 칸 수 = 의도한 칸 수, 그 밖의 변경 0칸»**을 확인한다. 브라우저 입력은 IME 첫 글자 유실·자동완성 끼어듦·포커스 어긋남으로 **오류 없이** 값을 잃는다 — 31칸 중 다수 유실·30여 칸 미반영이 diff 로만 드러났다(drip-chat-planning 155분, lifeManager 95분). 절차는 `00_briefs/standing/SOP_external-sheet-edit.md`.
9. **기기 폭 판정은 실제 폭 기준으로** (METH-149). 모바일 에뮬레이션이 `innerWidth` 를 늘려 넘침 0 으로 보이는 경우가 있다 — 기준 폭(예: 375px)을 명시하고 그 폭에서 `scrollWidth` 를 잰다(gamblescan). §2-2 의 측정 조건.

리팩터·마이그레이션 추가 규칙: **"결과 동일" 확인은 배선을 증명하지 않는다** — 소스를 일부러 바꿔 결과가 따라 바뀌는지 역방향 테스트. ID 재매핑은 "키로 조회하는 전 지점"을 명시 목록화(키 불일치는 에러 없이 null).

## 3. 검증불가 등록부 — 못 한 것을 됐다고 말하지 않는다

실사고 계보: 드래그·업로드·인증 UI를 브라우저 자동화로 검증 불가, 우회를 매번 재발명(lifeManager 6건 93분)·자격증명 필요 단계는 승인받아도 AI가 수행 불가(tshome).

1. **검증 못 한 항목은 명시적으로 등록한다** — 산출물·PR·checkpoint에 4필드로: *무엇을 / 왜 못 했나 / 대체 검증(한 것) / 확인 요청 대상(사람·실기기)*. "미검증 상태로 머지"는 가능하되 침묵은 금지.
2. **표준 우회 사다리** (재발명 금지): ① 데이터 직접 주입(execute_sql·시드) ② JS 직접 호출(`form.requestSubmit` 등) ③ 단위테스트로 쓰기 경로 커버 ④ 사람·실기기 확인 요청. 자격증명·결제·CAPTCHA는 처음부터 ④ — AI 불가 영역.
3. **비-포인터 대안 동반 구현**: 드래그·업로드류 UI는 탭/버튼 대안을 함께 만든다 — 미검증 상태로도 사용자가 막히지 않고, 대안 경로가 검증 가능 경로가 된다.
4. **리서치의 미확인 전제도 같은 규율로 이월한다** (METH-142). 조사 단계에서 확인 못 한 전제는 결론에 「미해결」로 **명시**해 이월하고, **그 전제에 의존하는 결정 직전에 1차 출처로 확인**한다. 미해결 표기가 없으면 틀린 가정이 결정에 조용히 스며든다. 실사례: 도구 무료 등급의 상업 사용 가부를 미해결로 남겨 두었다가 채택 결정 시 약관을 열었더니 「상업 제한」이 아니라 **「내보내기 자체 불가」** 였다 — 예산 선택지 하나가 통째로 사라졌다(icons). §1-3(못 한 것을 됐다고 하지 않는다)의 *조사* 버전이고, 확인 절차는 지침 24 §4(원문으로 검증)를 따른다.

5. **검증불가를 Done 의 미체크 항목으로 묻지 않는다** (METH-149). Done 으로 옮긴 항목 안에 `[ ]` 실기 확인이 남으면 등록부도 Blocked 도 아닌 곳에서 사라진다 — lifeManager Done 7건 중 4건. 사람·실기 확인이 남은 항목은 §3-1 등록부 + 외부 게이트면 TODO Blocked. **같은 벽이 2회 나오면 우회 수단을 만든다** — 로그인 벽 4회 재발(lifeManager)은 매번 우회가 아니라 **로컬 전용 테스트 계정 시드**가 답이다(값은 repo 시드 파일에, 지침 안전 규칙의 «자기 앱 테스트» 범위).
6. **에이전트 리허설 ≠ 사람 인수** (METH-149). 에이전트가 브라우저로 운영 절차를 연습한 것은 운영팀 리허설 통과를 대신하지 않는다. 인수 기준은 사람이 수행한 정량 기준(예: 30분 이내·클릭 10회 이내)으로 두고, 운영 피드백 항목은 «재현 소멸 증거»가 있어야 Done(비적용 팀 repo 의 운영 리허설 런북 관행).

## 4. 판정기의 신뢰도 — '통과'는 '거부'보다 약하다

실사고 계보: 파일럿 100곳에서 **거부 86건은 전부 타당했는데 통과 10건 중 5건이 가짜**였다(주차 도메인·타 브랜드 사이트·카지노 아님·지오블록 미매칭·모달 백드롭). 같은 세션에 3회 반복 — 로고(빈 이미지 4곳)·스냅샷(쿠키바 잔존)·캡처 자세(스크롤된 화면) 전부 가드는 통과시키고 눈으로만 잡혔다(gamblescan).

1. **통과 판정을 독립 확인 없이 최종으로 쓰지 않는다.** 자동 판정기의 두 출력은 신뢰도가 비대칭이다 — 거부는 "무언가 걸렸다"는 양성 증거지만, 통과는 "내가 아는 방식으로는 안 걸렸다"일 뿐이다. §1-3(negative case로 실효 증명)이 *가드 자체의* 실효성이라면, 이것은 *가드 출력의* 해석 규칙이다.
2. **적재·발행 직전에 육안 단계를 파이프라인에 남긴다.** 자동 판정만으로 통과시키는 경로를 만들지 않는다. 표본이라도 사람이 본다.
3. **탐지 규칙을 넓히기 전에 신규 적중분을 전수 재측정한다.** 그럴듯한 지문 하나를 근거 없이 넓혔다가 **운영 중인 대상 12곳을 비활성화할 뻔했고**, 적용 직전 재측정으로 막았다(GoDaddy `pdns##.domaincontrol.com` 을 주차 네임서버로 오독 — 실제로는 Premium DNS 라 A·MX 가 살아 있었다). 원칙: **살아있는 것을 내리는 오판이 죽은 것을 놓치는 것보다 나쁘다.**
4. **좁힐 때도 같다 — 기존 자산을 전수 재검증한다.** 스키마·규칙을 *좁히면* 이미 저장된 자산이 소급 위반이 된다. 상류 실사례: `repeat_of` 허용형을 나중에 좁히면서 5월 레거시 관찰로그를 재검증하지 않아 **CI 가 3회 연속 red 인 채로 아무도 몰랐다**(METH-132).
5. **판정 오라클은 관측 대상과 캐시·세션을 공유하지 않는 전용 표면에 둔다** (METH-142). 공용 표면을 반복 조회하는 것은 표본이 아니라 **같은 낡은 사본의 재확인**일 수 있다 — 관리자 변경 직후에는 낡은 사본이 다수라 다수결로도 못 이긴다. 방문자 트래픽과 캐시를 공유하지 않는 전용 프로브 페이지로 판정을 옮겨 반영 확인이 10분+ 에서 3~5초로 바뀌었다(cafe24-renewal). §4-1 이 판정 *출력*의 해석이라면, 이것은 판정 *대상 표면*의 선택이다.

6. **재발한 버그는 그 부류 전체를 단언으로 막는다** (METH-149). 같은 원인의 버그가 다시 나면 그 한 건을 고치지 말고 **클래스 전체의 불변식**을 테스트로 고정한다 — 「모든 STABLE 운영자 RPC 는 잠금에 닿지 않는다」 전수 단언(비적용 팀 repo — 선례를 커밋 본문이 인용). §1-6(문장→도구 승급)의 테스트판이고, friction `repeat_of` ≥2 와 같은 신호다.

## 4b. 공개 주장 릴리스 — 표면 매트릭스 (METH-137)

실사고 계보: 공개 신뢰 점수·주장 리셋 릴리스에서 프로덕션 CI 통과 후에도 **홈의 낡은 주장과 Overview 점수 링크가 잔존** — 후속 PR의 라이브 검증으로만 발견·제거(gamblescan PR-304→305).

1. **공개 주장 릴리스에는 표면 매트릭스를 만든다.** 바꾸려는 주장·수치·점수가 노출되는 공개 표면(홈·목록·상세·개요·OG/메타·사이트맵·외부 배포 링크)을 **전수 나열**하고 표면마다 확인 결과를 기록한다. 변경 diff에 없는 표면이 바로 stale 주장이 사는 곳이다 — §1-5(리드백)·§2-3(내용 기준)은 *만든 것*을 검증하고, 매트릭스는 *남아 있는 것*을 잡는다.
2. **확인은 렌더된 Preview·프로덕션 실서빙에서.** 코드 grep·CI green 은 릴리스 판정이 아니다 — §4-1(통과 판정은 약하다)의 릴리스 버전. 배포된 화면에서 주장이 실제로 갱신·제거됐는지 본다.
3. **Class C 게이트와 연동.** 공개 릴리스·브랜드/공개 메시지 변경(CLAUDE.md §3 Class C)의 검증 규범 측 대응물 — 매트릭스가 비어 있으면("노출 표면을 모름") 릴리스 판정 불가로 취급한다.

## 4c. 첫 공개·출시 보안 게이트 (METH-149)

실사고 계보(3개 repo): 데이터 접근 정책이 꺼진 채 출시돼 플랫폼 보안 경고로 뒤늦게 발견 · CI·브랜치 보호가 출시 뒤에야 도입 · 호스팅 배포 보호가 일부 별칭에는 적용되지 않음을 배포 후 비인증 요청으로 발견. 세부는 각 repo 정본.

1. **첫 공개 전, 호스팅·DB 플랫폼의 보안 진단(advisor)을 돌려 High 0건을 확인**한다. 스키마 변경 PR 마다 다시 돈다(Supabase `get_advisors` 등). 가드레일(CI·보호 규칙·접근 정책)은 **출시보다 먼저** 깐다 — 출시 뒤에 까는 가드레일은 그 사이의 노출을 되돌리지 못한다.
2. **배포 직후 비인증 요청으로 보호 상태를 실측**한다 — 보호 설정의 «켜짐»은 대리 신호다(§1-4). 운영 별칭·프리뷰·커스텀 도메인을 표면별로.
3. 민감 데이터와 공개 표면이 같은 DB 를 쓰면 접근 경로(공개 역할 정책·권한 상승 함수)를 전수 나열해 PR 에 남긴다 — Class B(인증·권한) 증거다.
4. **보안 약점의 구체(대상·범위·기간)는 공개 저장소 문서에 적지 않는다** — 교훈은 일반형으로, 세부는 비공개 정본에.

## 5. 적용 지점

- wrap 전 자기 점검: 이번 세션 "검증했다"고 보고하려는 항목이 §1-4(대리 신호)·§1-5(리드백)·§2-3(내용 기준)·§3-1(등록부)·§4-1(통과 판정)을 통과하는가. 공개 주장 릴리스면 §4b 표면 매트릭스가 있는가.
