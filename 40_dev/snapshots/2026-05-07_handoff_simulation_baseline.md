# 인계 시뮬레이션 #1 — 베이스라인

> ⚠️ 본 문서는 *snapshot* 입니다. 살아있는 운영 문서가 아닙니다. (CLAUDE.md §운영 규칙)

> 목적: `10_foundation/WHITEPAPER.md` §7-2(이식성·인계 지표)의 *최초 실측 데이터* 확보.
> 시점: L0 첫 구현체(`.ai/context.json` 등) 작성 직후.
> 목표는 "현 상태가 좋다는 증명"이 아니라 "*이후 측정과 비교 가능한 기준선*" 확보.

---

## 1. 시뮬레이션 프로토콜

### 1.1 시나리오

> 새 PC에서 처음 이 저장소를 받은 AI가, **`.ai/context.json` 만으로 시작**해 *추가 질문 없이* 다음 작업을 식별하고 첫 행동을 시작할 수 있는가.

### 1.2 측정 항목 (백서 §7-2 매핑)

| ID | 지표 | 백서 목표 | 본 회차 측정 가능성 |
|---|---|---|---|
| M1 | 부팅 시간 | ≤ 60초 | 부분(이론치 — must_read 토큰량 기반 추정) |
| M2 | 인계 성공률 | ≥ 95% | N/A (1회 시도로는 비율 산출 불가; 다음 회차부터) |
| M3 | 벤더 잠금 점수 (core) | 0 | ✅ 측정 |
| M4 | 검증된 모델 다양성 | ≥ 3 | ✅ 측정 |

### 1.3 한계 (정직 모드)

- **자기 자신을 시뮬레이션하는 한계**: 현 세션의 AI(claude-sonnet-4-6)는 이 작업의 *작성자* 이므로 "콜드 리드"가 불가능. 진짜 검증은 *다른 모델*에서 이 저장소를 받아 수행해야 함.
- **벤더 잠금의 *키워드-기반* 측정**: 키워드 매칭은 1차 근사. 더 미묘한 종속(예: 특정 도구의 명령 형식 가정)은 정성 검토 필요.
- **부팅 시간**: 실 측정 대신 토큰량 → 추론 시간으로 추정. 모델·네트워크별 편차 큼.

## 2. 측정 결과

### 2.1 M1 — 부팅 시간 (이론치)

`must_read` 파일 5개의 합산 크기:

| 파일 | bytes | lines |
|---|---:|---:|
| `.ai/context.json` | 1,050 | 41 |
| `ONBOARDING.md` | 3,083 | 72 |
| `10_foundation/WHITEPAPER.md` | 22,747 | 402 |
| `CLAUDE.md` | 7,210 | 189 |
| `.ai/checkpoint.md` | 4,259 | 70 |
| **합계** | **38,349** | **774** |

- 약 **38 KB ≈ 9–11K tokens** (한국어 비중 고려).
- 평균 LLM 추론 속도(50–100 tok/s)에서 **읽기 자체는 수 초 이내**, 첫 의미 있는 출력(요약+다음 행동 식별)까지 **30–60초** 추정.
- **판정**: 백서 목표(≤ 60초) **잠정 충족**. 다른 모델 실측에서 재확인 필요.

### 2.2 M2 — 인계 성공률 (N/A 이번 회차)

1회 시도로 비율 산출 불가. 다음 회차부터 누적:

```
인계 성공률 = (추가 질문 없이 다음 작업 시작한 시도 수) / (총 시도 수)
```

**최초 측정 가능 시점**: 다른 모델·다른 PC에서 동일 시나리오 1회 이상 실시 후.
**제안 다음 회차**: GPT-5(또는 Gemini)에서 깨끗한 클론으로 동일 프로토콜 수행.

### 2.3 M3 — 벤더 잠금 점수 (core)

**측정 범위 정의** (정량화를 위해 본 스냅샷이 *임시* 정의 — 다음 ADR로 정식화 필요):

```
core = .ai/context.json + .ai/checkpoint.md + .ai/schema/
     + 10_foundation/*.md
     + 60_tools/*.py
     + (root) README.md, CLAUDE.md, AGENTS.md, ONBOARDING.md
```

`.ai/adapters/` 는 *의도적으로 도구 종속* 영역이므로 core 제외.

**키워드 출현 횟수** (case-insensitive, `grep -rio`):

| 키워드 | 횟수 |
|---|---:|
| `claude code` | 0 |
| `claude-code` | 0 |
| `anthropic` | 0 |
| `openai` | 0 |
| `gpt-` | 0 |
| `cursor` | 0 |
| `windsurf` | 0 |
| `codex` | 0 |
| **합계** | **0** |

- **판정**: 백서 목표(0) ✅ **충족**.
- **단서**: 파일명 `CLAUDE.md` / `AGENTS.md` 자체가 *도구 명명 규칙* 이지만, 이는 백서 §5 L0 어댑터 패턴의 *듀얼 미러* 디자인이지 종속이 아님 — Claude/Codex/그 외 도구가 모두 같은 내용을 공유하므로 점수 산정에서 제외.
- **개선 여지**: 키워드 리스트는 시간이 지나며 갱신 필요(새 AI 도구 등장 시). 이 리스트 자체를 `60_tools/`에 스크립트로 박아야 자동 측정 가능.

### 2.4 M4 — 검증된 모델 다양성

- `50_resources/catalog/` 디렉터리 **미존재**.
- 등재된 Catalog 엔트리 = 0건.
- 따라서 `verified_with` 필드가 있는 엔트리 = 0건.
- **검증된 모델 다양성 = 0** (백서 목표 ≥ 3 **미달**, 예상된 결과)

이 격차는 백서 §10 *Stage 2 — 자산화* 단계에서 메우도록 설계되어 있음. Stage 1(현 단계) 종료 조건엔 포함되지 않음.

## 4. 확인된 격차 (다음 세션 우선순위)

> 본 시뮬레이션이 *드러낸* 결함. 다음 사람의 작업 우선순위로 직결.

### G1. methodology-source 자체에 HANDOFF.md / TODO.md 부재

- 현상: 본 저장소는 *방법론의 원천*이라 적용 프로젝트와 다른 운영 모드. 백서 §부록 A는 이를 명시하지만, *원천 저장소가 자신의 방법론을 자신에게 적용*하는 경우의 운영이 결정되지 않음.
- 영향: ONBOARDING 체크리스트의 "다음 작업 한 가지 식별"을 `.ai/checkpoint.md`에서 끌어와야 하는데, 적용 프로젝트와 절차 분기가 생김.
- **결정 필요**: methodology-source에도 HANDOFF/TODO를 둘 것인가? (ADR 제안)

### G2. Catalog/Skeleton 디렉터리 부재

- 백서 §5 L2가 약속한 핵심 자산:
  - `50_resources/catalog/`
  - `50_resources/skeletons/`
  - `50_resources/ai_observations/` (L1)
- 모두 *디렉터리 자체*가 없음. Stage 2 작업.
- **다음 단계**: 빈 디렉터리 + 각각의 `_README.md`(스키마 명세)를 우선 생성하면, 도메인 시드 추가 작업이 즉시 가능.

### G3. L1 관찰 로그 작성 규칙 문서 미작성

- 백서 §5 L1 + 8주 계획 1주차 산출물.
- `20_guides/03_AI_관찰_로그_작성_규칙.md` 미존재.
- **영향**: 매 세션 자동기록을 강제할 단일 규칙이 없어 어댑터 별로 표류 위험.

### G4. 컨텍스트 검증 자동화 부재

- `jsonschema` 미설치 → schema 적합성 검증 불가.
- CI도 미구성 → 백서 §9 리스크 1(L1 자동기록 누락)의 안전망 없음.
- **다음 단계**: `60_tools/` 또는 `methodology.py` 서브커맨드로 `validate-context` 구현.

### G5. 인계 성공률 측정 인프라 부재

- M2를 측정하려면 *다른 모델·다른 PC* 에서 시도 1회 이상 필요.
- **다음 단계**: 사용자가 GPT-5(웹 UI) 또는 Gemini에서 본 저장소를 받아 동일 프로토콜 시도. 그 결과를 `40_dev/snapshots/2026-05-NN_handoff_simulation_round2.md`로 기록.
