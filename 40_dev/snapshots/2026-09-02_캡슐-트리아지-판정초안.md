## A. 이미 반영 5건 — 상류 코드 실측 대조

어제(2026-09-01) METH-138~141 로 처리된 것들이 그 시점 발신 캡슐로 수거됐다. 상류 코드와 캡슐의 「확정 패턴」을 문자 단위로 대조했다.

**#1 land-billing-pattern** — 캡슐의 확정 패턴 `(^|/)(billing|payment|pricing|checkout|invoice|subscription)s?[./_-]|(^|/)plans?[._-](pricing|price|billing|tier|quota)` 이 `60_tools/methodology.py` `CLASS_BC_PATTERNS` 과금 항에 **그대로 있다**. 상류는 여기에 `|(^|/)plans[./]`(복수형 세그먼트)를 더 얹었다 — METH-139 에서 icons 병렬 수정과 합집합을 택한 결과다. 캡슐이 요구한 것 이상이 반영됐다.

**#2 asset-exts** — `ASSET_EXTS`(22종) + `_is_asset` + `_classify_change` 의 스킵 + `_excluded_assets`(무엇을 안 봤는지 출력)까지 캡슐의 4개 요구가 전부 있다. 캡슐이 명시한 경계(문서 확장자는 제외하지 않는다)도 주석과 테스트로 고정돼 있다.

**#3 repo-name-from-git-common-dir** — `_repo_name` 이 `git rev-parse --git-common-dir` 기준으로 교정돼 있다. **이번 수거가 그 검증이었다** — dry-run 105건이 실적재 24건으로 줄었고, icons 계열 워크트리 5곳이 전부 dedup 됐다.

**#4·#5 icons-wt-hub 2건** — 같은 제안의 앞선 관측이다. 발신처(icons)가 2026-09-01 에 3건을 #1 로 통합했고 그 통합본에 이력이 남아 있다. 통합 전 워크트리 사본이 origin 에 남아 있어 별도 id 로 수거됐다. **내용 판정은 #1 과 동일 — 이미 반영.**

> 이 5건은 반영 작업 없이 `_inbox` 정리 대상이다. 다만 #4 의 id 오염은 발신 시점 검증 부재의 잔재이므로, `capsule` 생성 시 id 검증을 넣자는 후속 후보(HANDOFF 기재)는 유지한다.

## B. 도구 변경 4건

### B-1. land 오탐이 운영자를 길들인다 (#6, 유효·부분)

**제안**: Class B/C 스캐너가 「파일에 결제 단어가 있는가」를 보지만 기준은 「결제 정책을 바꾸는가」다. 개행 0개 단일 라인 JSON 산출물은 한 글자만 바뀌어도 전 코퍼스가 추가된 줄로 잡혀 3회 연속 오탐했다. 용어별 순증(added−removed) 판정과 단일 라인 블롭 예외를 요구한다.

**조사**: 상류 `_classify_change` 는 `git diff --name-only` 만 쓴다 — **경로만 보고 내용은 안 본다**. 캡슐이 말하는 「추가된 줄의 결제 단어 수」 판정은 상류에 없다(하류 icons 의 자체 가드 또는 사람의 육안 판정으로 추정). 따라서 *제안된 수정 대상 코드가 상류에 없다*.

그러나 캡슐의 **핵심 관찰은 상류에 그대로 적용된다** — 상시 오탐이 사람을 「또 오탐」으로 길들여 진짜 위험을 통과시킬 뻔했다(#381 에 실제 신규 가격 12,000원이 있었다). 이 관찰은 METH-138(plan 오탐)·METH-141(자산 오탐)의 근거와 **같은 것**이고, 두 건 다 이미 그 논리로 처리됐다.

**판정 초안**: 유효(부분) — 내용 기반 순증 판정은 **상류 범위 밖**(경로 판정기에 콘텐츠 스캐너를 새로 만드는 일이라 Class 판정 설계 변경). 반면 「오탐이 가드를 죽인다」는 원칙은 이미 코드 주석에 박제됐다.
**분배 권고**: ① `CLASS_BC_PATTERNS` 헤더 주석에 이 실사례(#355·#356·#381, 오탐 3연속 후 진짜를 놓칠 뻔함)를 한 줄 추가해 근거를 박제한다. ② 콘텐츠 순증 판정은 **채택하지 않는다** — 경로 판정기의 단순함이 그 신뢰의 근거이고, 내용 판정은 Class B/C 를 사람이 보게 하는 현 설계와 겹친다. *대안*: 하류 icons 의 로컬 가드로 존치(그쪽이 산출물 형태를 안다).

### B-2. rotate 가 정렬을 가정만 한다 (#7, 유효·재현 확인)

**조사**: `_rotate_todo_done()` (methodology.py:3743) 은 `items[:keep]` 로 **문서 순서 상위 N건**을 남긴다. docstring 은 "최신 keep건"이라 적었지만 **정렬도 검증도 없다**. 캡슐 주장 그대로다.

**이 저장소에서도 재현된다** — 오늘 rotate 실행 직전 TODO Done 순서는 141·140·139·138·137·**116**·131·136·135 였다. 116 은 2026-07-25 인데 131·136·135(2026-08-07)보다 **위에** 있었다. keep=4 라 이번엔 피해가 없었지만 keep=6 이었다면 최신 131 을 버리고 116 을 남겼다.

**판정 초안**: 유효. **분배 권고**: `_rotate_todo_done` 이 항목의 날짜(본문 첫 날짜 토큰 또는 `- **date**` 필드)로 정렬한 뒤 자르고, 날짜를 못 읽는 항목이 있으면 **경고 후 중단**한다(조용한 아카이브 금지 — 지침 23 §1-1 무음 실패). negative case: 미정렬 TODO 픽스처로 최신 항목이 살아남는지 증명.

### B-3. build-guard.sh 만 옛 판정이 남아 있다 (#8, 유효·경로 절반 미반영)

**조사**: 상류에 dev 서버 감지가 **두 벌** 있다.
- `methodology.py::_dev_server_running` (3890행) — 이미 `lsof` 로 프로세스 cwd 를 확인해 **이 프로젝트 하위일 때만** 차단한다(METH-131, gamblescan 캡슐 반영). 캡슐이 요구한 바로 그 수정이다.
- `60_tools/build-guard.sh` — 여전히 `pgrep -fl "next dev"` **머신 전역**. 헤더 주석이 그 한계를 "미탐이 비싸니 보수적으로"라고 정당화한 채 남아 있다.

CLAUDE.md §2 는 수동 빌드를 `build-guard.sh` 경유로 지시한다 — **사람이 실제로 지나는 경로가 안 고쳐진 쪽**이다. 캡슐의 근거(오탐 4회 → FORCE 우회 습관 → `.next` 파괴 2회)는 이 경로에서 났다.

**판정 초안**: 유효. **분배 권고**: `build-guard.sh` 에 cwd 스코프 이식 — `pgrep -f` 결과의 각 PID 를 `lsof -a -p PID -d cwd -Fn` 로 확인해 스크립트 실행 위치 하위인 것만 차단, cwd 판정 불가는 안전측 차단 유지(파이썬 쪽과 동일 규칙). 자기 명령 문자열 자기적중(`pkill -f "next dev"`)도 함께 배제한다. 두 벌이 갈라지는 것 자체가 위험이므로, 장기적으로는 **셸이 `methodology.py` 판정을 호출**하는 단일화를 권고한다(지침 19 §8b.1 원시함수 단일화의 상류 자기적용).

### B-4. ship 이 남의 스테이징을 모른 채 커밋한다 (#9, 유효)

**조사**: `ship` 은 기본 `git add -A`(2934행), `--no-add-all` 이면 인덱스를 그대로 쓴다. **인덱스에 무엇이 담겼는지 확인하는 단계는 없다** — `git diff --cached --quiet` 로 "비었는가"만 본다. 캡슐이 지적한 구멍 그대로다.

**판정 초안**: 유효. **분배 권고**: commit 직전에 `git diff --cached --name-only` 를 세션이 만진 파일 집합과 대조해 **외부 스테이징이 있으면 목록을 보이고 확인을 요구**한다(`--assume-shared` 류 명시 플래그로만 통과). 기본 `add -A` 자체도 공유 체크아웃에서는 같은 위험이라, 아래 C 절의 「격리 워크트리 우선」 규율과 함께 간다.

## C. 동시 세션 git 격리 — 캡슐 2건 묶음 (#10·#11, 유효)

**조사**: `20_guides/` 전체에 **worktree·워크트리 언급이 0건**이다. CLAUDE.md 는 스택-PR 금지·main 직행 단일 PR·ship 단일 경로는 규율하지만 **한 체크아웃을 여러 세션이 공유할 때**를 다루지 않는다. 지침 08 은 *서브에이전트 팬아웃*(한 세션 안의 병렬)이라 축이 다르다.

두 캡슐은 같은 사고의 앞뒤다.
- #10: 브랜치 전환·커밋·배포가 서로를 덮는다 → origin/main 기반 격리 워크트리에서 작업·커밋·PR·배포. 함정: 워크트리엔 `.vercel/project.json` 이 없어 배포가 **새 프로젝트를 만든다**.
- #11: 격리하지 않은 채 「경로 지정 git add」로 막으려 했더니 실패했다 — 같은 파일의 다른 블록을 남이 편집 중이면 파일 단위 스테이징이 남의 훅을 통째로 가져간다. `add -A` 없이 사고가 났다. 착수 전 `git status` 로 미추적 파일만 보는 것으로는 부족하고, **이미 추적 중인 파일 안의 미커밋 편집**이 진짜 함정이다.

이 저장소도 같은 사고를 겪었다 — 지침 22 전파 때 icons 에서 브랜치 전환 레이스로 sync 커밋이 남의 피처 브랜치에 유입됐다(HANDOFF Recent 2026-08-22, 이력 오염 존치 판단).

**판정 초안**: 유효 — **두 건을 한 절로 병합**한다(1제안 1캡슐 규칙은 발신 측 granularity 이고, 반영은 주제 단위가 맞다).
**분배 권고**: 지침 08 에 §9 「동시 세션 격리」 신설(또는 신설 지침 30 — 사람 판단). 내용 4항: ① 같은 repo 에 세션이 둘 이상이면 **origin/main 기반 격리 워크트리에서 시작**한다 ② 공유 체크아웃에서는 경로 지정 add 도 안전장치가 아니다 — 파일이 겹칠 가능성이 있으면 `add -p` 또는 워크트리 ③ 착수 전 확인은 미추적 파일이 아니라 **추적 파일의 미커밋 편집**까지 본다(`git diff --stat`) ④ 워크트리 배포는 `.vercel/project.json` 등 링크 파일을 먼저 복사한다(안 하면 새 프로젝트가 생긴다). ## D. 구조 있는 텍스트의 편집 사고 — 2 repo 재현 (#12·#13, 유효·N≥2)

**조사**: 지침 19 §8b.2(METH-131 반영)가 이미 「일괄 치환은 범위를 최소로·카나리 검증」을 규율한다. 두 신규 캡슐은 **같은 계열의 새 실패 모드**를 가져왔고, 서로 다른 repo(icons·cafe24-renewal)에서 왔다 — catalog 승급 기준의 N≥2 를 충족한다.

- #12(icons): 비탐욕 범위 매칭도 서식이 바뀌면 경계를 넘는다. 표 구분선 일괄 치환이 무관한 5열 표를 6열로 깨뜨렸고, 한 줄로 압축된 배열을 스캔하다 다음 export 두 개를 삭제했다. 대응 = **행 단위 편집 + 편집 후 구조 검증**(헤더·구분선 열 수 비교).
- #13(cafe24): ①범위 삭제 전 삭제 본문 확인 + 배포 전 함수 정의 인벤토리(문법 검사는 통삭제를 못 잡는다 — **9분 라이브 노출**) ②치환은 `subn` 건수 assert(0건 no-op 가 조용한 미배포를 만든다) ③검증과 업로드를 한 셸 체인으로(중단 후 버전만 올라간 실사고) ④파일 전체 blanket replace 금지.

②는 지침 23 §1-1(0건 처리 = 실패)의 편집 인스턴스이고, ④는 §8b.2 재확인이며, ①③은 신규다.

**판정 초안**: 유효(둘 다). **분배 권고**: 지침 19 §8b.2 를 확장하고 §8b.3 「구조 편집·배포 원자성」을 신설한다 — 행 단위 편집·편집 후 구조 검증(열 수·정의 인벤토리)·치환 건수 assert·검증과 배포의 원자 체인. 실사고는 두 repo 것을 모두 적는다(계보가 규칙의 수명을 늘린다). §8b.2 에 이미 있는 카나리 규칙과 중복되지 않게 「치환 전 범위 축소」와 「편집 후 구조 검증」을 명시 분리한다.

## E. 착수·판단 규율 3건 (#14·#15·#16, 유효)

### E-1. 진단 없는 리서치 (#14)

**조사**: 지침 24 §2 는 「조사·문서의 *진단*은 착수 시점에 코드로 재확인」이다 — **이미 있는 진단의 검증**이다. 캡슐은 한 칸 앞을 말한다: 「수준이 부족하다」류 모호 요청에는 **진단이 아예 없으므로, 해결책 리서치 전에 현행 산출물을 실측해 진단부터 만든다.** 실사례가 강하다 — 소음이 유일한 실패 조건인 잠입 게임에 오디오 0개, 6.8MB 스프라이트 참조 0회, 이동이 CSS transition. 이 7행이 리서치 결론을 「좋은 도구 목록」에서 「바닥 교체가 선행」으로 뒤집었다.

지침 24 §3 의 「모호 요청은 범위를 질의」와도 직교한다(그건 범위, 이건 현황 실측).

**판정 초안**: 유효. **분배 권고**: 지침 24 §2 에 2번째 불릿으로 편입 — "진단이 없으면 만든다: 개선 요청은 해결책 탐색 전에 현행 산출물을 실측해 결함 목록을 만든다. 실측 없는 도구 리서치는 일반론으로 흐른다."

### E-2. 규칙을 쓰기 전에 정본을 읽는다 (#15, target 재배치 권고)

**조사**: 캡슐 target 은 guide-19(클린코드)지만 내용은 **코드 규칙이 아니라 규칙 저술 절차**다 — 상위 결정을 인용하며 범위를 넓히고 재확인이라 서술, 정본 규칙을 안 읽고 배제, ADR 에 없는 자체 가드레일을 정본처럼 인용해 사용자 요구를 금지로 단정. 한 세션에 세 번 났다.

지침 24 §1(정본 확인)·§4(사용자가 그은 경계는 원문 검증)와 **같은 축**이다. 다만 24 는 전부 *읽기·판정* 쪽이고, 캡슐은 *쓰기* 쪽이다 — 새 규칙·금지를 저술할 때의 선행 독해 의무는 없다.

**판정 초안**: 유효 — **target 을 guide-19 → guide-24 로 재배치**한다.
**분배 권고**: 지침 24 §4b 신설 「규칙·금지를 쓰기 전에 정본을 읽는다」 3항: ① 상위 결정을 인용해 범위를 넓히지 않는다 — 인용은 원문 범위 안에서만 ② 금지를 쓸 때는 **적용 범위를 명시**한다(무조건 금지가 다른 정당한 용법을 위반으로 만든다) ③ ADR·정본에 없는 자체 가드레일을 정본처럼 인용해 사용자 요구를 거절하지 않는다.

### E-3. 미해결 전제를 결정 직전에 재확인 (#16)

**조사**: 지침 23 §3(검증불가 등록부)은 *검증* 축의 같은 원리다 — 못 한 것을 됐다고 하지 않고 4필드로 등록한다. 캡슐은 이를 **리서치 전제** 축으로 확장한다: 확인 못 한 전제를 「미해결」로 명시 이월하고, **그 전제가 걸린 결정 직전에 원문 실확인**. 실사례 = 도구 무료 등급의 상업 사용 가부를 미해결로 두었다가 채택 결정 시 약관 확인, 「상업 제한」이 아니라 「내보내기 자체 불가」로 가정이 뒤집혀 예산 선택지 하나가 사라졌다.

**판정 초안**: 유효. **분배 권고**: 지침 23 §3 에 4번째 항 추가(등록부의 리서치 버전) — "리서치의 미확인 전제는 결론에 「미해결」로 명시 이월하고, 그 전제에 의존하는 결정 직전에 1차 출처로 확인한다. 미해결 표기가 없으면 틀린 가정이 결정에 스며든다." 지침 24 §4(원문 검증)와 상호 참조.

## F. 제작 게이트·게임 검증 3건 (#17·#18·#19, 유효)

### F-1. 회색 상자 관문 (#17)

**조사**: 지침 25 §5 게이트 ②(풀 퀄리티 진입 — 1차 패스 통과분의 고비용 렌더 승인)가 이미 같은 원리다. 지침 26 §3(클린 베이스 승인)·27 ①④(저가 1차 패스)가 그 도메인 인스턴스다. 캡슐은 여기에 **두 가지를 더한다**: ① 게임·인터랙션 도메인의 저비용 대리물 정의(네모와 선만으로 규칙을 굴려 재미를 사람이 판정) ② **정지 규칙** — 3회 조정에도 불합격이면 설계를 폐기 ③ **예산 결합** — 유료 도구 결제는 해당 단계 도달 시점에만(월 $22 를 재미 판정 뒤로 미룸).

### F-2·F-3. 헤드리스 검증 가능한 게임 로직 (#18) · 임베디드 프리뷰 캔버스 함정 (#19)

## G. 검증 측정 2건 (#20·#21, 유효)

### G-1. 도구가 다르면 결과도 다르다 (#20)

**조사**: 5항 중 3항이 지침 23 의 기존 조항에 **새 인스턴스로 붙는다**.
- ①「같은 URL 이라도 curl 무쿠키 변형은 다른 사본」 — §1-4(대리 신호를 사실로 쓰지 않는다)의 **가장 강한 신규 사례**다. curl 6/6 「딜없음」 vs 브라우저 2/2 「신선」으로 '원복 실패' 오판이 2회 났다. 기존 §1-4 사례는 요약 도구·컬럼명·카운트 쿼리였고, **HTTP 클라이언트 변형**은 새 축이다.
- ②「textContent 는 숨긴 자식을 포함한다 → 요소별 노출여부(display·offsetHeight) 포함 덤프로 판정」 — §2-3(존재가 아니라 내용·가시성)의 구체 기법.
- ③「버전 게이트 폴링 후에만 측정」 — §1-5(리드백) 의 타이밍 조건.
- ④캐시 시나리오는 route 로 페이지만 위장하고 판정 조회는 실서버 통과 ⑤깜빡임은 16ms 샘플링으로 정량화 — 기법이라 도메인성이 강하다.

**판정 초안**: 유효. **분배 권고**: ①②③을 지침 23 해당 항의 실사고 계보·기법으로 편입(①은 §1-4 에 "HTTP 클라이언트 변형은 다른 사본을 준다 — 판정은 실사용 경로로"). ④⑤는 `_pending/P-004`(#19 와 같은 「임베디드·자동화 환경 검증 기법」 묶음)에 합치거나 별도 pending — 사람 선택.

### G-2. 판정 오라클은 전용 표면에서 (#21)

**조사**: 캡슐 본문의 절반은 Cafe24 캐시 4계층 모델(플랫폼 고유)이지만, **판정 규칙 한 줄은 도메인 무관하게 일반적이다** — "관리자 변경 직후엔 낡은 사본이 다수라 다수결로도 못 이긴다. 방문자 트래픽과 캐시를 공유하지 않는 **전용 프로브 페이지**를 판정 오라클로 삼는다." 반영 지연 10분+ 를 3~5초로 만든 실측이 근거다. 지침 23 §4(판정기의 신뢰도)에 없는 축이다 — §4 는 판정 *출력*의 해석이고, 이건 판정 *대상 표면*의 선택이다.

**판정 초안**: 유효(일반화분만). **분배 권고**: 지침 23 §4 에 5번째 항 — "판정 오라클은 관측 대상과 캐시·세션을 공유하지 않는 전용 표면에 둔다. 공용 표면에서의 반복 조회는 표본이 아니라 같은 낡은 사본의 재확인일 수 있다." 4계층 모델 자체는 #24 와 함께 하류 존치.

## H. 문체 1건 (#22, 유효)

**조사**: 지침 05 §9b(METH-137, 같은 ai-icons SOP 에서 온 6항)에 **대시 조항이 없다**. 상류 지침 전체에도 없다. 캡슐의 핵심은 규칙 자체의 결함이다 — 종전 규칙이 「대시 뒤는 값·범위·시점·근거만 허용」이라 **근거를 허용해 재발을 방치**했고, 같은 지적을 세 번 받은 뒤에야 원인이 규칙임을 확인했다. 새 판정은 기계적이다: 「대시 앞이 완결 문장(다·요로 끝남)이면 대시를 쓰지 않는다」, 허용은 목록 예고와 라벨-값 표기 2종. 굵게 표시를 제거한 뒤 판정해야 누락이 없다. 한 파일에서 33건 적발.

**같은 SOP 발 2번째 캡슐**이다(1번째 = METH-137 로 §9b 가 됐다). 같은 도메인 N≥2 이므로 catalog 가 아니라 기존 절 보강이 맞다.

**판정 초안**: 유효. **분배 권고**: 지침 05 §9b 에 7항 신설 — 판정 규칙·허용 2종·굵게 제거 후 판정. 함께 **메타 교훈 한 줄**을 §9b 서두에 적는다: "금지 규칙에 예외 목록을 넉넉히 두면 그 목록이 재발 경로가 된다 — 예외는 형태(라벨-값)로 한정하고 의미(근거)로 열지 않는다." 이 교훈이 §9b 의 나머지 6항에도 적용된다.

## I. 플랫폼 고유 2건 (#23·#24)

**#24 cafe24-platform-findings (상류 미반영 권고)**
내용이 전부 Cafe24 고유 사실이다 — `@layout` 없는 커스텀 html 의 렌더 동작, `product_detaildesign` 이 방출하는 표시항목, `{$item_title}` 어트리뷰트 파손, 타임세일 앱의 재렌더 주기, SFTP 반영 ~50초. 상류 catalog 는 「재발한 문제 1건당 1엔트리」의 **교차 프로젝트** 자산이고, 이 지식은 한 플랫폼·한 repo 안에서만 재사용된다. 하류에 이미 정본이 있다(`20_constraints/cafe24-limits.md` — 상류엔 이 디렉터리 관례 자체가 없다).

**판정 초안**: 상류 미반영(기각 아님 — **하류 정본 존치**). **분배 권고**: 캡슐 회신 대신, 일반화 가능한 메타 규칙 한 줄만 승급 검토 — "플랫폼·벤더 고유 제약은 repo 로컬 정본(`20_constraints/` 류)에 두고 상류로 올리지 않는다. 상류로 올리는 것은 **다른 플랫폼에서도 참인 규율**뿐이다." 이 한 줄은 캡슐 `_README` §1(포인터+요약 원칙) 옆에 두면 발신 노이즈를 줄인다. 사람 판단 필요.
